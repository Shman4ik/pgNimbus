# Автодополнение SQL: второй аудит — удобство набора

Статус: аудит, 27 сентября 2026 года. Проверенная ревизия: `29c5299b8738ed84b52a05cbdeba5d0bd1d15fce`.
Сделано: пакет K (буквальный набор — 0 расхождений с автоалиасом и без, проверка идёт в каждой сборке; оракул 28,4% / 29,2%), пакет L (ступени совпадения, грамматика допустимых ключевых слов, внутренние функции и секции по фактам каталога, частота по подключению; ключевые слова первыми после двух символов 94%, предложенные слова 93%, оракул 32,9% / 33,9%, с порогом 32% в каждой сборке), пакет M (таблица C01 — тест, многословные ключевые слова одной строкой и их сокращения, OVER/FILTER по виду функции, CASE, `*`, MERGE; корпус вырос до 30 запросов, оракул на нём 31,5% / 32,4% → 35,3% / 36,4%, на исходных 25 — 35,0% / 36,0%; порог 35%), пакет O (системные отношения с pg_catalog первой, встроенные функции, метки enum и TRUE/FALSE после сравнения, последовательности, поля даты, факты колонок и аргументы со значениями по умолчанию; непредложенных слов по вине каталога 0 из 508, остальные — новые имена 3,0%, объявленные позже, пакет R, 9,1%, DDL, пакет N, 0,6%; оракул 38,5% / 38,9%, порог 38%).
Первый аудит и его пакеты A–I: [sql-editing-experience.md](sql-editing-experience.md). Он исправил точность разбора: границы команд, области видимости, search_path, приём подсказки одной правкой.
Этот аудит измеряет другое: сколько работы подсказки экономят при обычном наборе, где они мешают, и чего не хватает до лучшего автодополнения на рынке. План — пакеты K–R в разделе 7.

## 1. Коротко

- **Разбор запроса — сильная сторона.** CTE, производные таблицы, LATERAL, коррелированные ссылки, search_path, кавычки, условия JOIN по каждому FK, `excluded.` в ON CONFLICT, типы после `::`, подсказка аргументов. Здесь pgNimbus на уровне лидеров, местами точнее.
- **Enter портит текст при обычном наборе.** 25 обычных запросов, набранных по строкам с Enter в конце строки, дали 51 расхождение с набранным текстом. 30 из них меняют текст, 21 — проглоченный перевод строки. Четыре заменяют таблицу одноимённой таблицей другой схемы, в том числе в `UPDATE` и `DELETE`. `IS NULL` превращается в `IS nullif(`, алиас `c` — в `CROSS`.
- **Ранжирование ставит нечёткое совпадение выше точного.** `em` выбирает `error_message`, а не `email`; `AS` — представление `account_seats`; `WH` после условия JOIN — `WHEN`. Ключевые слова вне начала команды стоят ниже всего каталога. Нужное слово первым после двух символов — 59% слов, для ключевых слов 61%.
- **Покрытие PostgreSQL заканчивается на SELECT и DML.** DDL, служебные команды, системные каталоги, большая часть встроенных функций, значения enum, параметры `SET`, роли не подсказываются. 18% слов корпуса не предлагаются ни при каком префиксе. При этом 372 внутренние функции расширений (`ltree_in`, `gtrgm_out`, `hnsw_bit_support`) выходят в список наравне с `count`.
- **Экономия нажатий у пользователя, который всегда выбирает лучшую строку, — около 25%.** Цель пакетов — не меньше 45% на том же корпусе.

Порядок работ: K «не навреди» → L ранжирование → M грамматика ключевых слов → O каталог → P конструкции целиком → N DDL и служебные команды → Q отображение и настройки → R набор «сначала колонки».
K и L — P0: без них остальные улучшения подсказок видит только тот, кто смотрит на список перед каждым Enter.

## 4. Находки

Приоритеты те же, что в первом аудите: P0 — подсказка меняет смысл или синтаксис текста; P1 — ежедневные сценарии; P2 — удобства; P3 — идеи.
`|` в примерах — курсор, `⏎` — Enter.

### 4.1. Не навреди: Enter при обычном наборе — P0

Буквальный набор, 51 расхождение, выключенный автоалиас:

| Что произошло | Раз | Пример: набрано → получилось |
| --- | --- | --- |
| Enter принял строку, совпадающую с набранным словом, перевод строки не вставлен | 21 | `ON c.id = o.customer_id⏎` → строка не переносится |
| Алиас заменён ключевым словом | 7 | `FROM customers c⏎` → `FROM customers CROSS` |
| Алиас заменён таблицей | 6 | `FROM saas.projects p⏎` → `FROM saas.projects saas.plans` |
| Таблица заменена одноимённой таблицей другой схемы | 4 | `UPDATE customers⏎` → `UPDATE commerce.customers` |
| Ключевое слово заменено функцией или колонкой | 4 | `WHERE a.deleted_at IS NULL⏎` → `IS nullif(`; `ORDER BY sold DESC⏎` → `ORDER BY sold description` |
| Имя дополнено до более длинного существующего | 3 | `m.name AS manager⏎` → `AS manager_id`; `SELECT pid, state, query⏎` → `query_string` |
| Изменён регистр ключевого слова | 3 | `= true⏎` → `= TRUE` |
| Лишняя `)` в конце запроса после `nullif(` | 3 | следствие строки выше |

С включённым автоалиасом картина та же: 51 расхождение, алиасы дописываются к уже испорченным вставкам (`FROM commerce.orders o`).
`FROM customers c⏎` → `CROSS` воспроизведено в живом окне.

**A01. Enter принимает строку, которая ничего не меняет.** Пользователь набрал `customer_id` целиком, список показывает `customer_id`, Enter принимает её, и перевод строки теряется. Это 21 случай из 51: строка, которая заканчивается именем из списка, требует двух Enter.
Причина: правило §6.1 первого аудита считает префиксное совпадение уверенным выбором и не проверяет, изменит ли приём текст.
Требование: Enter принимает строку, только если приём меняет текст. Иначе список закрывается и Enter вставляет перевод строки. Так работает режим `acceptSuggestionOnEnter: "smart"` в VS Code. Изменение только регистра ключевого слова считается отсутствием изменения (см. F02).

**A02. Алиас в конце строки заменяется ключевым словом.** `FROM customers c⏎` → `CROSS`, `orders o` → `ORDER`, `saas.issues i` → `INNER`, `saas.users u` → `UNION`, `org.employees e` → `EXCEPT`, `w` → `WHERE`.
Причина: после законченного элемента FROM список поднимает WHERE, JOIN, ORDER и т. д. (`FromItemFollowItems`), а Enter принимает любое префиксное совпадение. Одна буква — самый частый алиас и одновременно префикс ключевого слова.
Требование: позиция сразу после элемента FROM или JOIN, где может стоять алиас, — позиция нового имени. Там Enter принимает только строку, выбранную стрелками, мышью или Ctrl+Space. Tab по-прежнему принимает выделенную строку.

**A03. Алиас заменяется таблицей.** `FROM saas.accounts a⏎` → `FROM saas.accounts saas.accounts`, `projects p` → `saas.plans`, `subscriptions s` → `saas.sessions`, `invoices inv` → `saas.invoices`, `devices d`, `teams t`.
Причина та же: для букв, с которых не начинается ни одно ключевое слово продолжения, список показывает таблицы, а Enter принимает префиксное совпадение. Вставка к тому же квалифицирована схемой.
Требование то же, что для A02. Дополнительно: в позиции алиаса первой строкой можно предлагать алиас, который выбрал бы автоалиас (`c` для `customers`).

**A04. Набранная таблица заменяется таблицей другой схемы.** `FROM orders⏎` → `FROM commerce.orders`, `UPDATE customers⏎` → `UPDATE commerce.customers`, `DELETE FROM order_items⏎` → `DELETE FROM commerce.order_items`.
При search_path = `public` имя `orders` означает `public.orders`. После Enter запрос читает, обновляет или удаляет строки другой таблицы. Для UPDATE и DELETE это риск для данных.
Причины: в позиции таблицы строки идут в порядке схем по алфавиту (`commerce` раньше `public`), search_path не учитывается; вставка всегда квалифицирована, поэтому приём «меняет текст» и проходит правило Enter.
Требование: голое имя, которое разрешается по search_path, первым предлагает именно разрешённое отношение. Таблица другой схемы с тем же именем никогда не выбирается раньше неё. Вставка — без схемы, если имя однозначно (F01).

**A05. Ключевое слово заменяется функцией или колонкой.** `IS NULL⏎` → `IS nullif(`, в конце запроса остаётся лишняя `)`. `ORDER BY sold DESC⏎` → `ORDER BY sold description`.
Причина: при равной оценке совпадения `nullif` (функция, приоритет 3) выигрывает у `NULL` (ключевое слово, приоритет 0), `description` (колонка, 100) — у `DESC`. Точное совпадение имени не ставится первым.
Требование: строка, имя которой точно совпадает с набранным словом, стоит первой (B01). Вместе с A01 это даёт перевод строки после `NULL⏎` и `DESC⏎`.

**A06. Новое имя заменяется существующим.** `AS manager⏎` → `AS manager_id`, `AS last_order⏎` → `AS last_order_at`. В сценариях: `SELECT count(*) AS n⏎` → `notifications`, `c.email AS e⏎` → `employees`, `FROM public.customers AS c⏎` → `saas.comments`.
Причина: после AS список ведёт себя как в выражении, хотя там пишется новое имя.
Требование: после AS (вне `CAST(… AS`), имя CTE, имя в `CREATE …`, имя колонки в определении таблицы — позиции нового имени, как в A02.

**A07. Регистр ключевых слов меняется.** `= true⏎` → `= TRUE`. Синтаксис верный, но редактор переписывает стиль пользователя, который пишет в нижнем регистре. Решается через F02 и A01.

**A08. Список открыт после 71% нажатий.** Для редактора кода это нормально, но при правилах Enter выше каждый Enter становится ставкой. После K частота открытия не критична; её стоит снизить только в позициях нового имени.

### 4.2. Ранжирование — P0

Исходные значения — раздел 3. Причины воспроизводятся на уровне `CompletionRanker`.

**B01. Нечёткая оценка решает раньше точного и префиксного совпадения.** `CompletionRanker` сортирует по баллу `FuzzyMatcher`, и только при равном балле смотрит на совпадение начала и приоритет контекста. Бонус начала слова (4) больше бонуса соседней буквы (2), поэтому аббревиатура выигрывает у настоящего префикса:

| Набрано | Где | Первая строка | Нужная строка |
| --- | --- | --- | --- |
| `em` | SELECT без FROM | `error_message` | `email` |
| `is` | WHERE | `ivfflat_bit_support()` | `is_active`, `IS` |
| `up` | начало команды | колонка `unit_price` | `UPDATE` |
| `GR` | после WHERE-условия | `gen_random_uuid()` | `GROUP` |
| `AS` | после выражения в SELECT | представление `account_seats` | `AS` |
| `oi` | `ON p.id = oi` | колонка `order_id` | алиас `oi` |
| `su` | SELECT | колонка `seats_used` | `sum()` |

Первый аудит (§6.3) предписывал ступени: точное совпадение, начало имени, начала частей имени, прочий нечёткий поиск. Реализация их не соблюдает.
Требование: ступени — отдельный ключ сортировки перед приоритетом контекста. Внутри ступени — приоритет контекста, частота использования, балл, длина.

**B02. Ключевые слова всегда ниже каталога.** Вне начала команды и позиции после элемента FROM у ключевых слов приоритет 0 — ниже колонок каталога (5), функций (3) и таблиц (10). Результаты: `DESC L` → `lag()` вместо `LIMIT`, `= false W` → `word_similarity()` вместо `WHERE`, `= 'x' a` → `avg()` вместо `AND`, `WH` после условия JOIN → `WHEN` вместо `WHERE`, `c.id = 1 o` → `ON`, который в WHERE недопустим.
Требование: у ключевого слова приоритет зависит от того, допустимо ли оно здесь (C01). Допустимое продолжение стоит в группе текущей команды, недопустимое не показывается.

**B03. search_path не влияет на порядок отношений.** `FROM cu` выбирает `commerce.customers`, `FROM ord` — `commerce.orders`, хотя search_path = `public`. Это источник A04.

**B04. В начале команды предлагается весь каталог.** В начале команды допустимы только команды, но `up` выбирает колонку `unit_price`, `al` — функцию `array_length`, `dr` — `dense_rank`, `not` — таблицу `notifications`.
В списке команд нет `MERGE`, `VALUES`, `TABLE`, `LISTEN`, `NOTIFY`, `UNLISTEN`, `LOCK`, `REINDEX`, `CLUSTER`, `DISCARD`, `PREPARE`, `EXECUTE`, `SAVEPOINT`, `RELEASE`, `START`, `END`, `CHECKPOINT`, `IMPORT`, `REASSIGN`.

**B05. Порядок пустого запроса случаен для пользователя.** После `SELECT ` первыми видны SELECT, FROM, WHERE, INSERT, INTO, VALUES, UPDATE — порядок массива `Keywords`. После `FROM ` сначала семь схем, затем отношения схемы `analytics`, потому что она первая по алфавиту.

**B06. GROUP BY выбирает агрегат.** `SELECT status, count(*) FROM public.orders GROUP BY |` выделяет `count` — выходное имя `count(*)`. Группировать по агрегату нельзя. Нужная строка — `status`, а лучше строка «все неагрегированные колонки» (P).

**B07. Колонки после `alias.` не учитывают FK.** `JOIN saas.users u ON u.id = i.|` ставит первой `id`, а не `assignee_id` и `reporter_id`, которые ссылаются на `users.id`. При втором JOIN той же таблицы полезнее FK, который ещё не использован.

**B08. История принятий живёт до конца сессии.** `CompletionRecency` хранит 50 последних принятий в памяти окна. Частоты нет, после перезапуска всё сначала. DataGrip ранжирует с помощью модели, обученной на выборе пользователей.

**Прототип ранжирования.** На том же корпусе проверен черновой ранжировщик (в репозиторий не вошёл) со ступенями (точное совпадение, начало имени, начала частей, подстрока, остальное), фильтром внутренних функций расширений по имени и приоритетом ключевых слов 6 вместо 0:

| Ключевые слова, 175 слов | Первым @1 / @2 / @3 | В пятёрке @1 / @2 / @3 |
| --- | --- | --- |
| Сейчас | 36% / 61% / 85% | 50% / 83% / 99% |
| Прототип | 47% / 77% / 88% | 87% / 97% / 99% |

Прототип выявил и обратную сторону: без проверки допустимости короткие ключевые слова `OR`, `IN`, `NOT` точно совпадают с набранными `or`, `in`, `no` и вытесняют `orders`, `interval`, `now()` там, где эти слова недопустимы (`FROM or|`). Поэтому L и M делаются вместе: сначала отсечь недопустимое, потом ранжировать.

### 4.5. Каталог — P1

**E01. Системных каталогов нет.** `pg_catalog` (142 отношения) и `information_schema` (69) не загружаются: `FROM pg_stat_act|`, `information_schema.|`, `pg_catalog.|` — пустой список. Для клиента PostgreSQL это ежедневные запросы (`pg_stat_activity`, `pg_locks`, `pg_class`, `information_schema.columns`). В корпусе такие слова составляют большую часть 72 непредложенных.
Схема `pg_catalog` неявно стоит первой в search_path, поэтому `pg_class` разрешается без схемы. Разрешение коротких имён в провайдере это тоже должно учитывать.

**E02. Встроенные функции предлагаются по списку из ~100 имён.** `pg_size_pretty`, `pg_total_relation_size`, `pg_terminate_backend`, `to_timestamp`, `regexp_matches`… не предлагаются, хотя их сигнатуры уже загружены для подсказки аргументов. `current_date`, `current_timestamp`, `current_user`, `localtimestamp` — ключевые слова-функции, их нет нигде.
Из 2 719 имён pg_catalog после исключения функций с аргументами `internal`/`cstring`, функций ввода-вывода типов, реализаций операторов и обработчиков остаётся 1 116 имён. Описания есть в `pg_description`.

**E03. Внутренние функции расширений засоряют список.** 372 из 379 функций пользовательских схем принадлежат расширениям в `public`. Это функции ввода-вывода (`ltree_in`, `gtrgm_out`), реализации операторов (`vector_lt`, `word_similarity_commutator_op`), поддержка индексов (`hnsw_bit_support`, `gin_extract_value_trgm`). Они выигрывают у нужных слов: `LI` → `ltree_in` вместо `LIMIT`, `HA` → `hstore_to_array` вместо `HAVING` (31-е место).
Требование: исключать по фактам каталога (`pg_type.typinput/typoutput/…`, `pg_operator.oprcode`, `pg_amproc`, `pg_aggregate`, псевдотипы), а не по именам. Функции расширений, которые пользователь вызывает (`similarity`, `gen_random_uuid`, `crypt`), остаются.

**E04. Дубликаты.** `gen_random_uuid` показан дважды: из встроенного списка и из `pgcrypto`.

**E05. Секции таблиц — как обычные таблицы.** `FROM r|` показывает `iot.readings` и восемь секций `readings_2026_01…07`, `readings_default`. Секции нужны редко; их стоит скрывать или показывать ниже родителя.

**E06. Мало сведений об объектах.** Представление, материализованное представление, секционированная и внешняя таблицы выглядят как таблица. У колонок нет PK, FK, NOT NULL, значения по умолчанию, комментария; у таблиц — комментария и оценки числа строк. Подсказка аргументов показывает `account_mrr(p_account_id bigint, p_at date)` и скрывает, что `p_at` имеет значение по умолчанию: читаются `identity arguments`, а не `pg_get_function_arguments`.

**E07. Нет значений.** После `i.status = |` и внутри `'…'` для enum-колонки нет меток (`'open'`, `'in_progress'`…); после `= ` для boolean — TRUE/FALSE ниже `trim()`. Нет последовательностей в `nextval('|')`, полей в `extract(|)` и `date_trunc('|')`, ролей, расширений.
Метки enum — данные каталога (`pg_enum`), их можно загрузить вместе с типами без запросов на нажатие.

**E08. Набор «сначала колонки».** При наборе слева направо `SELECT c.fi|` ничего не предлагает: алиас `c` появится только в FROM. Это 34 из 107 обращений через точку в корпусе. `SELECT first|` без FROM предлагает `first_name` одной строкой без указания таблицы и не дописывает FROM.

### 4.6. Вставка — P1 / P2

**F01. Таблицы в FROM и JOIN всегда вставляются со схемой.** `cu` → `public.customers c`, хотя `customers` однозначно разрешается по search_path. Пользователь, который пишет без схем, не может принять подсказку и набирает имя целиком: именно поэтому `customers` и `orders` возглавляют список слов, набранных руками. TablePlus выносит это в настройку «Auto prefix schemas».
Рекомендация: по умолчанию схема только при необходимости (имя не разрешается или разрешается в другую таблицу); настройка «всегда со схемой» — в Preferences.

**F02. Ключевые слова всегда в верхнем регистре.** Нет настройки и нет учёта стиля документа. TablePlus («Auto uppercase keywords») и DataGrip дают выбор. Рекомендация: по умолчанию регистр, в котором пользователь набирает, с настройкой UPPER/lower.

**F03. Оконные функции вставляются без OVER.** `row_number()` → `row_number()`; DataGrip дописывает `OVER ()` и ставит курсор внутрь.

**F04. Нет конструкций целиком.** Строки, которые в DataGrip принимаются одним приёмом: JOIN с алиасом и условием по FK, список колонок INSERT, «все колонки» после SELECT, «все неагрегированные колонки» после GROUP BY, раскрытие `*` прямо в списке (сейчас только команда палитры). Подробнее — пакет P.

**F05. `(` не принимает функцию.** `coun(` оставляет `coun()` и закрывает список. Для строк-функций `(` можно сделать символом принятия, когда набранное — начало имени.

### 4.7. Отображение и подсказки — P2

- **G01.** Совпавшие буквы в строке не выделяются. При нечётком поиске непонятно, почему строка попала в список.
- **G02.** Правый столбец (тип, схема, имя FK) — 11 px с прозрачностью 0,55. На экране с высокой плотностью в живом окне он почти не читается.
- **G03.** Боковая подсказка содержит только вид объекта («keyword», «column · customers»). Нет типа с NOT NULL, ссылки FK, значения по умолчанию, комментария, для таблицы — вида и числа строк.
- **G04.** Строка под указателем мыши подсвечивается почти как выбранная; в живом окне их легко спутать.
- **G05.** Home и End двигают выделение в списке, а не курсор в строке (поведение стандартного `CompletionList`).
- **G06.** Подсказка аргументов остаётся поверх палитры команд и после ухода фокуса из редактора (живое окно).
- **H01.** Особые формы SQL: `extract(field FROM x)`, `substring(x FROM y FOR z)`, `position(a IN b)`, `trim(…)`, `overlay`, а также `coalesce`, `greatest`, `least`, `nullif`, которых нет в `pg_proc`. Подсказка отсутствует или показывает сигнатуру функции вместо синтаксиса.
- **H02.** Перегрузки не упорядочены по типу аргумента: для `upper(` первой идёт `upper(anymultirange)`.

### 4.8. Что уже на уровне лидеров

Эти свойства нужно сохранить и защитить тестами при переделке ранжирования:

- области видимости: CTE, производные таблицы, LATERAL, коррелированные подзапросы, UNION, скрытие имён;
- разрешение имён по search_path, кавычки, регистр;
- условия JOIN по каждому FK, включая составные и два FK к одной таблице, с именем ограничения;
- объединённые колонки USING/NATURAL, `excluded.` только от DO до RETURNING;
- приём одной правкой с одним Undo, автоалиас без повторов, повторное использование `(`;
- списки колонок INSERT, SET, ON CONFLICT, USING;
- типы после `::` и `CAST(… AS`, подсказка аргументов с именованными параметрами;
- раскрытие `*` с отказом, когда форма результата изменилась бы;
- задержки: открытие списка меньше 1 мс на этом каталоге, большие документы читаются вне UI-потока.

## 6. Целевое поведение

Раздел дополняет контракт §6 первого аудита. Изменение правила Enter (6.1) требует решения владельца, как и в прошлый раз.

### 6.1. Клавиши

- **Enter** принимает выделенную строку, если выполнены оба условия: строку выбрали (стрелки, мышь, Ctrl+Space) или набранное — начало её имени; и приём меняет текст. Изменение только регистра ключевого слова изменением не считается.
- **В позиции нового имени** (алиас после элемента FROM/JOIN, после AS, имя CTE, имя в CREATE, имя колонки в определении таблицы) Enter принимает только строку, выбранную явно.
- **Tab** принимает выделенную строку всегда, как сейчас.
- **Escape**, пробел, запятая и `;` не принимают строку, как сейчас.
- **`(`** принимает строку-функцию, если набранное — начало её имени (F05).

Проверка правила — буквальный набор корпуса: 0 расхождений.

### 6.2. Порядок строк

1. Отсечь недопустимое в позиции: в начале команды — только команды; после FROM — отношения и CTE; после законченного выражения — операторы и ключевые слова продолжения; в позиции нового имени — предложенный алиас и ключевые слова продолжения.
2. Ступень совпадения: точное имя → начало имени → начала частей (`oi` → `order_items`) → подстрока → остальное.
3. Внутри ступени — группа контекста: имена текущей команды, затем объекты search_path, затем остальной каталог.
4. Затем частота и давность принятия для этого подключения, затем длина, затем стабильный порядок.

Для пустого запроса порядок задаёт контекст, а не порядок массивов: после `SELECT ` — колонки источников, `*`, частые функции; после `FROM ` — отношения search_path по частоте использования.

| Где | Строка | Результат |

Значение в `VALUES (…)` получает подсказку, как аргумент функции: имя и тип колонки текущей позиции.

### 6.5. Каталог

Один снимок, как сейчас, с добавлениями: вид отношения и признак секции; флаги колонок (PK, FK, NOT NULL, DEFAULT, identity, generated) и комментарии; метки enum; последовательности; роли; параметры сервера из `pg_settings`; доступные расширения; системные отношения и их колонки; встроенные функции с описаниями и без внутренних; аргументы функций со значениями по умолчанию.
Чтение остаётся фоновым, без запросов на нажатие. Системные каталоги не зависят от базы данных пользователя и могут загружаться один раз на версию сервера.

### 6.6. Отображение

Совпавшие буквы выделены; правый столбец читаемый; боковая подсказка показывает то, что нужно для выбора: тип и флаги колонки, ссылку FK, комментарий, вид и оценку строк отношения, сигнатуру и описание функции.
Никаких новых постоянных элементов интерфейса (правило 1 DESIGN.md).

### 6.7. Настройки

Три пункта в Preferences, без кнопок на панели: регистр ключевых слов (как набираю / UPPER / lower), схема перед таблицей (при необходимости / всегда), Enter (как в 6.1 / принимать только Tab).

## 7. План

Оценки относительные. Нумерация продолжает первый аудит; пакет J (шаблоны, локальная диагностика, системные объекты) распределён по M, O и P.

| Пакет | Приоритет / размер | Работа | Зависит от | Критерий завершения |
| --- | --- | --- | --- | --- |
| K. Не навреди | P0 / S–M | Правило Enter 6.1 (изменение текста, позиции нового имени), точное совпадение первым, разрешённое по search_path отношение первым | — | `CompletionTypingReplayTests`: 0 расхождений с автоалиасом и без, `[Explicit]` снят с буквального набора; тесты A01–A06 |
| L. Ранжирование | P0 / M | Ступени совпадения, отсечение недопустимого, группы контекста, фильтр внутренних функций и секций по фактам каталога, дубликаты, частота по подключению, колонки по FK после `alias.` | K | Ключевые слова первыми после двух символов ≥ 90%, все предложенные слова ≥ 85%; ни одного выбора из другой схемы при однозначном имени |
| M. Грамматика ключевых слов | P1 / M–L | Продолжения C01, многословные ключевые слова и сокращения, `*`/AS/FROM в SELECT, OVER/FILTER/CASE, исправление позиций LIMIT, UNION, GROUP, MERGE USING | L | Таблица C01 проходит как тест; KSR ≥ 35% |
| O. Каталог шире | P1 / M | E01–E07: системные отношения с разрешением через `pg_catalog`, встроенные функции с описаниями, функции-ключевые слова, метки enum, последовательности, роли, параметры, расширения, виды отношений, флаги и комментарии колонок, аргументы со значениями по умолчанию | L | Непредложенных слов корпуса ≤ 3% |
| P. Конструкции целиком | P1 / M | Таблица 6.4, подсказка колонки в VALUES | M, O | KSR ≥ 45% на корпусе |
| N. DDL и служебные команды | P1 / L | D01–D02 через грамматику слотов: шаблон команды — последовательность ключевых слов и типизированных слотов (отношение, колонка отношения, тип, роль, функция, параметр) | M, O | Таблица D01 и сценарии 20–25 приложения Б дают нужные списки |
| Q. Отображение и настройки | P2 / M | G01–G06, H01–H02, настройки 6.7, F02 | K | Скриншоты в обеих темах; тест настроек |
| R. Сначала колонки | P2–P3 / M | E08: колонки по будущему алиасу (`c.` → таблицы с алиасом `c`) и строки «колонка · таблица» с дописыванием FROM | L, O | Обращения через точку в корпусе, набранном слева направо, предлагаются ≥ 90% |

Порядок: K → L → M → O → P → N → Q → R. K и L меняют поведение, к которому пользователи уже привыкли, поэтому идут первыми и отдельно от новых возможностей. M без L не работает: без отсечения недопустимого короткие ключевые слова вытесняют имена (прототип в 4.2).

Контрольные значения после каждого пакета — те же, что в разделе 3: расхождения буквального набора, KSR оракула, точность по словам, доля непредложенных слов, задержка открытия списка.

## 8. Воспроизведение

Стенд лежит в [`tools/CompletionBench/Audit`](../../tools/CompletionBench/Audit/) (подробности в его README):

| Файл | Что это |
| --- | --- |
| `catalog.json` | Снимок каталога стенда, прочитанный `SqlCompletionProvider.ReadCatalogAsync` — тем же чтением, что и обновление каталога в редакторе |
| `corpus.sql` | Корпус (приложение А) |
| `saas.sql` | Схема `saas`; загружается после `scripts/demo` 01–06 |
| `cases.txt`, `hints.txt` | Сценарии и вызовы для подсказки аргументов |

Инструменты:

| Команда | Что меряет |
| --- | --- |
| `dotnet run -c Release --project tools/CompletionBench -- quality` | Точность по словам и список промахов (раздел 3) |
| `… -- cases`, `… -- hints` | Ответ провайдера в каждом сценарии, подсказки аргументов |
| `… -- dump "<строка подключения>"` | Новый `catalog.json` с живой базы |
| `dotnet test --project PgNimbus.App.Tests -- --treenode-filter "/*/*/CompletionTypingReplayTests/*"` | Буквальный набор (утверждение: 0 расхождений) и оракул (KSR в отчёте теста, `TestResults/*.tunit-report.json`) |

На момент аудита `CompletionTypingReplayTests` был помечен `[Explicit]`, потому что буквальный набор падал. Пакет K сделал его зелёным и снял `[Explicit]` с буквального набора, пакет L — с оракула: обе проверки идут в каждой сборке.
Порог оракула не даёт метрике ухудшиться; каждый пакет, который поднимает KSR, поднимает и порог (после L — 32%, после M — 35%). Пакет, который добавляет запросы в корпус, сначала меряет на расширенном корпусе базовую ветку: цифры до и после сравниваются на одном корпусе.

Добавляя грамматику, добавляйте запросы в корпус: проверка буквального набора ловит именно тот класс ошибок, который не видят тесты с готовым текстом.
